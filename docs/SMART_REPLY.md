# Smart reply

Context-aware reply chips and a better "Needs a reply" mark, fully on device. No network, nothing stored,
no text leaves the phone. Code: `app/src/main/java/com/inboxiq/app/reply/`. Entry points:
`QuickReplySuggester.needsReply(...)` (inbox row) and `ReplySuggester` / `RulesReplySuggester` (thread chips).

## What it does

1. **Gate first** (`ReplyGate`). Before any wording is chosen it decides whether a reply may be suggested at all.
   Nothing is offered for: a message the user wrote last; labels PROMO / SPAM / SCAM / OTP_2FA (the thread label
   or the message's own); short codes, alphanumeric senders, toll-free numbers, email gateways, group addresses;
   OTP / verification text (reuses `OtpExtractor` and `TriageEngine.rulesOnly`); text the rules read as promo,
   scam or spam; texts that look auto-generated ("do not reply", "STOP", "out of office"); anyone asking you to
   send, read or share a code or PIN; links or location pins and "who is this / wrong number" probes from a number
   you have never talked to or saved; an MMS with no text and no picture, or a picture from a stranger.
   The classifier is read, not edited.
2. **Intent** (`IntentClassifier`). The newest unanswered text (and up to 3 before it, since your last message) is read
   sentence by sentence: yes/no (with availability / did-you / are-you-ok / want-to / opinion), open question
   (when / where / why / opinion / "guess what"), either-or (offers the two words it can read safely), scheduling
   (proposal or "what time works"), request (call me, let me know, help, money), thanks, apology, greeting, check-in,
   congratulations, good news, bad news, ETA ask, ETA update (late / arrived / on my way), sharing a link, photo or
   location, appointment reminder (confirm / reschedule), farewell, plain acknowledgement, tapback reaction, statement.
   A bare nudge ("ok?") does not outrank the real ask above it.
3. **Wording** (`ReplyBank`, `Composer`, `UserStyle`). Up to three short replies per intent, with formal / neutral /
   casual variants, chosen by a stable hash of the incoming text so chips do not flicker. `UserStyle` is rebuilt on the
   fly from what the user already sent (this thread weighted heavily, then everything recent, 300 rows read-only
   through `ReplyHistoryDao`; nothing is persisted, no schema change):
   emoji only if the user uses them (their own favourite, never on bad news), lowercase starts, dropped final period,
   exclamation habit, formality, and **their own phrasings**: if they usually say "yup works for me", that appears as the
   affirmative chip. Learned phrases must be short and free of digits, links, names and questions.
4. **Safety net** (`ReplySafety`). Every chip, from any source, must be under 80 characters with no link, number,
   code or password word, no money word, no "yes" to a money ask, and no exclamation or emoji on bad news.
5. **Needs a reply** uses the same intent. Marked: a question, a request, an ETA ask, a scheduling ask, a reminder to
   confirm, bad news, a check-in. Not marked: ok, thanks, greetings, reactions, shares, FYI, farewells, statements,
   automated senders, groups. The label-only check remains for the notification inline-reply action.
6. Chips are computed in a `produceState` on `Dispatchers.Default`, never on the main thread.

## Generative tier

`GenerativeReplySuggester(model: ReplyModel?)` is built and tested with a fake model. It only runs when the rules
already decided a reply is needed (so the model never sees an OTP, promo, scam or automated sender), under a hard
timeout (600 ms), keeps at most two lines that pass `ReplySafety`, and falls back to the rules on null, timeout,
exception or unusable output. **No production `ReplyModel` is wired**: the optional Gemma tier is only reachable through the Play
asset pack and `GemmaClassifier` is a classifier, not a text generator, so connecting it would be unverifiable here. When a
generator exists, pass it to `ThreadScreen(suggester = GenerativeReplySuggester(model))`.

## Evaluation

`SmartReplyEvalTest` (JVM) runs the old heuristic (frozen as `LegacySuggester` in the test sources) and the new engine over
`app/src/test/resources/smartreply/corpus.tsv` (253 obviously fake conversations, generated by
`scripts/smartreply/gen_corpus.py`, 555-01xx style numbers) and `challenge.tsv` (52 hand-written, free-form conversations).
The generated set was written alongside the rules and is an optimistic ceiling; the hand-written set was written once and is the
number to believe. Both are small. Definitions:

- Coverage: messages that deserve a reply that got at least one chip.
- Inappropriate: messages that must stay silent (codes, promos, scams, short codes, groups, acks, user-last...) that got any chip. Target 0.
- Needs-reply recall / false marks: the mark on messages that need a reply / marks anywhere else.
- Intent accuracy: the intent equals the label (old suggester has no intents).
- Relevance: rule-based, e.g. a yes/no question must include a yes-style option, thanks a "you're welcome", bad news a sympathy option without "!".

| Set | n | Suggester | Coverage | Inappropriate | Needs-reply recall | False marks | Intent accuracy | Relevance |
|---|---|---|---|---|---|---|---|---|
| generated | 253 | old | 100.0% | 82.7% (62/75) | 100.0% | 117 | n/a | 59.6% |
| generated | 253 | new | 100.0% | 0.0% (0/75) | 100.0% | 0 | 97.1% | 98.8% |
| hand-written | 52 | old | 100.0% | 90.5% (19/21) | 100.0% | 29 | n/a | 64.5% |
| hand-written | 52 | new | 95.2% | 0.0% (0/21) | 95.2% | 0 | 93.5% | 96.4% |

The old suggester's 100% coverage is not a virtue: it offered "Yes / No / Let me get back to you" to codes, promos and scams.
Known misses on the hand-written set: `so what are we doing about the car situation` (a question with no question mark; left
unmarked on purpose, since treating every unpunctuated "what ..." as a question would mark statements) and
`you still want to do the 8:30 showing or should we bail` (read as scheduling rather than yes/no; chips are still sensible).

Latency (rules tier, JVM, warmed): p50 0.13 ms, p95 0.35 ms, max 0.56 ms per request over 305 conversations; budget 50 ms,
asserted in `SmartReplyEvalTest` (p95 < 50 ms, max < 200 ms) plus a 200-message, 5000-word stress case. Texts are read only up
to 1200 characters. A phone is slower than this laptop, but there is two orders of magnitude of headroom.

## Not verified

Real device behaviour and real conversations (the device was off limits). Quality of wording for languages other than
English: the engine is English only and degrades to "no chips" rather than wrong chips, but that is untested beyond a few cases.
